# Authoring Guide: New Blog Posts

This guide documents the conventions for writing new posts on blog.mithis.net (Jekyll,
Barthelme theme). The audience is Tim (sole author). All sections reflect conventions
established by the P0–PSC migration phases.

This file lives in `docs/` which is excluded from the Jekyll build via `_config.yml`'s
`exclude: [docs/]`. It does not appear in the generated site.

---

## 1. Front Matter

All posts require YAML front matter between `---` delimiters. Two variants:

### WordPress-imported posts (existing corpus — all 76)

```yaml
---
author: mithro
categories:
- <slug>              # one or more category slugs (see §3 below)
date: YYYY-MM-DDTHH:MM:SS+ZZZZ   # ISO 8601 with timezone offset (from WP export)
excerpt: >
  First 1–2 sentences of the post, ending with '...' (auto-generated by WP exporter)
layout: post
permalink: /archives/<primary-category>/<wordpress_id>-<slug>
title: Post Title Here
wordpress_category: <primary-category-slug>
wordpress_id: <integer>
wordpress_url: https://blog.mithis.net/archives/<category>/<id>-<slug>
---
```

Do not modify these keys in existing posts.

### New (non-WP-imported) posts

```yaml
---
author: mithro
categories:
- <slug>
date: YYYY-MM-DD 12:00:00 +1000
excerpt: 'One or two sentence summary ending with ...'
layout: post
permalink: /archives/<primary-category>/<slug>
title: Post Title Here
---
```

The `wordpress_category`, `wordpress_id`, and `wordpress_url` keys are deliberately absent
for new posts. The post layout derives the comment lookup slug from `page.path` when
`wordpress_url` is absent.

**Key invariants:**

- `author:` is always `mithro` (lowercase).
- `layout:` is always `post`.
- `categories:` is a YAML list, even for a single category — never a bare scalar.
- `date:` for new posts: use `YYYY-MM-DD HH:MM:SS +1000` format (matches PSC-era posts).
- `excerpt:` must be present; the home and category layouts use it via
  `post.excerpt | strip_html | truncatewords: 30`. Keep it under 50 words.
- `permalink:` must begin `/archives/`; for new posts without a WP ID:
  `/archives/<primary-category-slug>/<slug>`.

## 2. Creating a New Post (scaffold script)

Use the scaffold script to generate a correctly-formatted stub:

```bash
uv run python scripts/new_post.py \
    --title "Post Title Here" \
    --slug my-post-slug \
    --date 2026-05-20 \
    --categories hardware,python
```

The script:
1. Generates `_posts/YYYY-MM-DD-<slug>.md` with correct new-post front matter.
2. Refuses to overwrite an existing file.
3. Warns on unrecognized category slugs (see §3 for the full list).

Defaults: `--date` defaults to today; `--categories` defaults to `uncategorized`.

Before committing, run the content linter:

```bash
uv run python -m scripts.fidelity.lint_content _posts --asset-root .
```

Zero findings required. The CI build gate (`lint_content` step in `.github/workflows/jekyll.yml`)
will fail the build on any non-zero result.

## 4. Adding a New Category

Copy `category/hardware.md` as a template:

```yaml
---
layout: category
title: My New Category
cat_slug: my-new-category   # MUST be cat_slug, NOT category
permalink: /archives/category/my-new-category/
description: ""
redirect_from:
  - /category/my-new-category/
---
```

**Why `cat_slug:` and NOT `category:`:**
Jekyll reserves the `category` and `categories` variables on page objects. Using
`category: my-new-category` on a `category/*.md` page causes `site.pages | where:
"category", …` to silently return empty results — the post layout can no longer find
the display name for that category (it falls back to the raw slug). The three layouts
(`post.html`, `category.html`, `home.html`) all use `site.pages | where: "cat_slug", slug |
first` for cross-page lookups; this only works when `cat_slug:` is set.

The live category feeds (`category/*/feed.xml`) keep `category:` in their own front
matter deliberately — they use `page.category` for same-page filtering, not cross-page
lookup, so the reserved-word trap does not apply to them. Do NOT normalize feed.xml
files to `cat_slug:`.

Also add one `<option>` to the `<select>` dropdown in `_includes/sidebar.html`:

```html
<option value="{{ '/archives/category/my-new-category/' | relative_url }}">My New Category (0)</option>
```

Update the count manually when posts are assigned. See `_includes/sidebar.html` for the
comment explaining the deferred dynamic-count option.

## 5. Image Convention

Images go in `/assets/images/` (year subdirectories are conventional):

```markdown
![Alt text describing the image](/assets/images/2026/my-image.png)
```

- Use plain `/assets/…` paths — no `{{ '/assets/…' | relative_url }}` Liquid.
  `baseurl` is `""` (custom domain, P4), so plain paths are correct and linter-clean.
- For linked thumbnails: `[![alt](thumb-path)](full-path)`.
- If you need a link `title=` attribute (hover tooltip), an inline
  `<a href="…" title="…"><img alt="…" src="…"/></a>` is permitted (link `title` is
  genuinely Markdown-inexpressible). Annotate with the `fidelity-allow` sentinel if the
  linter flags it.

## 6. Permalink Format

For new posts (no WP ID):

```
/archives/<primary-category-slug>/<post-slug>
```

Where `<post-slug>` is lowercase and hyphen-separated. Example:
`/archives/hardware/my-new-board-bring-up`

For WP-imported posts the permalink is already set; do not change it.

## 7. Content Conventions

### Smart quotes

Use curly quotes (`"` `"` `'` `'`) in the Markdown source where original prose had them.
Straight quotes are also fine for new posts — be consistent within a post.

### Faithful Markdown structure

- Blank lines between paragraphs.
- Correct indentation for nested lists (2- or 4-space).
- Do NOT flatten multi-paragraph sections into one block (a WP→MD export artifact fixed
  in P2; new posts must not repeat it).

### No hardcoded structural HTML

Do NOT use `<div>`, `<ul>`, `<ol>`, `<li>`, `<p>`, `<h1>`–`<h6>`, `<table>`, `<pre>`,
etc. in post Markdown. The content linter (`scripts/fidelity/lint_content.py`) will fail
the CI build if these are found.

Inline HTML is permitted where Markdown cannot express the original intent (e.g. `<abbr>`,
`<kbd>`, `<img>` with extra attributes, `<a title="…">`).

For genuine necessary-embed HTML (e.g. a Flash embed, a video iframe), annotate with the
`fidelity-allow` sentinel:

```html
<!-- fidelity-allow: BLOCK_HTML necessary-embed — <reason why Markdown cannot express this> -->
<object data="...">...</object>
```

The sentinel is per-occurrence, not file-wide. It suppresses exactly one BLOCK_HTML
finding on the annotated line (or the line immediately following the sentinel).

## 8. Comment Data Format

If a post will have comments, you MUST create BOTH forms in `_data/comments/`:

**Requirement:** `_includes/comments.html` resolves `site.data.comments[slug]` to the
directory hash when both forms exist. If only the `.yml` exists, the include uses the list
fallback path (robust as of P5-D). Both forms are required for full compatibility.

**Aggregate file `_data/comments/<slug>.yml`:**

```yaml
- date: YYYY-MM-DD HH:MM:SS +0000
  id: '<integer>'
  message: '<p>Comment text here.</p>'
  name: Commenter Name
  wordpress_url: https://blog.mithis.net/archives/...#comment-<id>
```

**Directory `_data/comments/<slug>/comment-<id>-<YYYYMMDD>-<HHMMSS>.yml`:**

```yaml
date: YYYY-MM-DD HH:MM:SS +0000
id: '<integer>'
message: '<p>Comment text here.</p>'
name: Commenter Name
wordpress_url: https://blog.mithis.net/archives/...#comment-<id>
```

The filename convention is `comment-<id>-<YYYYMMDD>-<HHMMSS>.yml` (zero-padded date/time,
matching the 10 existing individual comment files under `_data/comments/`).

## 9. Pre-Commit Checklist

Before committing a new post:

1. Run the content linter: `uv run python -m scripts.fidelity.lint_content _posts --asset-root .`
   — must exit 0.
2. Run the structure check: `uv run python -m scripts.fidelity.structure_check`
   — must pass 6/6.
3. Run the full test suite: `uv run python -m pytest tests/ -q` — all green.
4. Build locally: `bundle3.3 exec jekyll build` — no warnings, no errors.
5. Verify the post appears at its expected permalink in `_site/`.

The CI workflow (`.github/workflows/jekyll.yml`) enforces steps 1 and 4 automatically
on every push to `main`.

`_includes/category-feed.xml` (deleted), `_posts/*.md` (EOF normalization only),
`scripts/fidelity/lint_content.py` (minor polish), `.github/workflows/jekyll.yml`
(lint gate injection), and tests.

## §A — New-post authoring workflow

### A-1. Authoring document: location and justification

**File:** `docs/AUTHORING.md`

**Justification over `CONTRIBUTING.md`:** `CONTRIBUTING.md` is the GitHub/OSS convention
for "how to contribute patches to a shared project". This repo has no external contributors
and is a personal blog migration. The audience of the authoring doc is Tim (the sole author)
writing new blog posts. `docs/AUTHORING.md` is the conventional Jekyll/static-site location
for site-specific authoring instructions, and the `docs/` directory is already the project's
home for migration specs and plans. The file is excluded from the Jekyll build via
`_config.yml`'s `exclude: [docs/]` so it will not appear in `_site/`.

### A-2. Content of `docs/AUTHORING.md`

The document must cover (in this order, as sections):

#### A-2.1 Front-matter template

The exact corpus shape, established by P0–PSC. Two variants:

**WordPress-imported post (existing corpus):** all 10 keys:
```yaml
---
author: mithro
categories:
- <slug>              # one or more category slugs (see §3 below)
date: YYYY-MM-DDTHH:MM:SS+ZZZZ   # ISO 8601 with timezone offset
excerpt: >
  First 1–2 sentences of the post, ending with '...' (auto-generated by WP exporter;
  keep for fidelity)
layout: post
permalink: /archives/<primary-category>/<wordpress_id>-<slug>
title: Post Title Here
wordpress_category: <primary-category-slug>
wordpress_id: <integer>
wordpress_url: https://blog.mithis.net/archives/<category>/<id>-<slug>
---
```

**New (non-WP-imported) post:** the `wordpress_*` keys are NOT present. Required keys:
```yaml
---
author: mithro
categories:
- <slug>
date: YYYY-MM-DD HH:MM:SS +1000   # or +0000; use local timezone
excerpt: One or two sentence summary ending with '...'
layout: post
permalink: /archives/<primary-category>/<slug>
title: Post Title Here
---
```

`wordpress_category`, `wordpress_id`, `wordpress_url` are deliberately absent for new posts.
The post layout derives the comment lookup slug from `page.path` when `wordpress_url` is absent
(see `_layouts/post.html` slug-derivation block).

**Key invariants from the corpus:**
- `author:` is always `mithro` (lowercase).
- `layout:` is always `post`.
- `categories:` is a YAML list (even if one item); never a bare scalar.
- `date:` for new posts: use `YYYY-MM-DD HH:MM:SS +1000` format (matches PSC-era posts).
- `excerpt:` must be present (the home layout and category layout use it via
  `post.excerpt | strip_html | truncatewords: 30`); keep it under 50 words.
- `permalink:` must begin `/archives/`; for new posts without a WP ID:
  `/archives/<primary-category-slug>/<slug>`.

#### A-2.3 Image convention

Images go in `/assets/images/` (subdirectories by year are conventional:
`/assets/images/YYYY/`). Reference them with plain Markdown paths:
```markdown
![Alt text describing the image](/assets/images/2026/my-image.png)
```
- No `{{ '/assets/…' | relative_url }}` Liquid — `baseurl` is `""` (custom domain,
  set in P4), so plain `/assets/…` paths are correct and linter-clean.
- For linked thumbnail images: use `[![alt](thumb-path)](full-path)`. If you need a
  link-level `title=` attribute (hover tooltip), an inline `<a href="…" title="…"><img
  alt="…" src="…"/></a>` is permitted by the project's spec §7 justification (a link
  `title` is genuinely Markdown-inexpressible). Use `<!-- fidelity-allow: BLOCK_HTML
  necessary-embed — <reason> -->` if the linter flags it — but prefer Markdown.

#### A-2.4 Permalink format

For new posts (no WP ID): `/archives/<primary-category-slug>/<post-slug>` where
`<post-slug>` is a lowercase hyphen-separated slug (no special characters). Example:
`/archives/hardware/my-new-board-bring-up`.

For WP-imported posts the permalink is already set; do not change it.

#### A-2.5 Established conventions (P2/P3/P4/PSC era)

- **UTF-8 smart quotes in source:** use curly quotes (`"` `"` `'` `'`) in the Markdown
  source where the original prose had them (per M1/M2+R-P4 precedent). Straight quotes
  are also fine for new posts — just be consistent within a post.
- **Faithful Markdown structure:** blank lines between paragraphs; correct indentation for
  nested lists (2- or 4-space). Do NOT flatten multi-paragraph sections into one block of
  text (this was a WP→MD export artifact fixed in P2; new posts must not repeat it).
- **No hardcoded structural HTML in posts:** no `<div>`, `<ul>`, `<ol>`, `<li>`, `<p>`,
  `<h1>`–`<h6>`, `<table>`, `<pre>`, etc. The content linter (`lint_content`) will fail
  the CI build if these are found. Inline HTML is permitted where Markdown cannot express
  the original (e.g. `<abbr>`, `<kbd>`, `<img>` with extra attributes, `<a title="…">`).
  For genuine necessary-embed HTML (e.g. a Flash embed, a video iframe), annotate with
  the `fidelity-allow` sentinel:
  ```html
  <!-- fidelity-allow: BLOCK_HTML necessary-embed — <reason> -->
  <object data="...">...</object>
  ```
- **Comments — both-forms requirement:** if a post will have comments added to
  `_data/comments/`, you MUST create BOTH forms: the aggregate
  `_data/comments/<slug>.yml` file AND the `_data/comments/<slug>/` directory of
  individual per-comment files. The `_includes/comments.html` include iterates the
  directory hash (Jekyll resolves `site.data.comments[slug]` to the directory hash when
  both exist); if only the `.yml` exists, the include renders zero comments. See §A-2.7
  for the exact per-comment file format.

#### A-2.6 Adding a new category page

Copy `category/hardware.md` as a template. The critical point:

```yaml
---
layout: category
title: My New Category
cat_slug: my-new-category   # <-- MUST be cat_slug, NOT category
permalink: /archives/category/my-new-category/
description: ""
redirect_from:
  - /category/my-new-category/
---
```

**Why `cat_slug:` and NOT `category:`:**
Jekyll reserves the `category` and `categories` variables on page objects. Using
`category: my-new-category` on a `category/*.md` page causes `site.pages | where:
"category", …` to silently return empty results — the post layout can no longer find
the display-name for that category (it falls back to the raw slug). The three category-
consuming layouts (`post.html`, `category.html`, `home.html`) all use
`site.pages | where: "cat_slug", slug | first` for cross-page lookups; this only works
when the category `.md` sets `cat_slug:`. The live category feeds (`category/*/feed.xml`)
keep `category:` in their own front matter deliberately — they use `page.category` for
same-page filtering, not for cross-page lookup, so the reserved-word trap does not apply
to them. Do NOT "normalize" feed.xml files to `cat_slug:`.

Also add one `<option>` to the `<select>` dropdown in `_includes/sidebar.html`:
```html
<option value="{{ '/archives/category/my-new-category/' | relative_url }}">My New Category (0)</option>
```
Update the count manually when posts are assigned to it (the sidebar uses static integers
— see §A-2.8 for the sidebar dynamic-count USER-DECISION item).

#### A-2.7 Comment data format (for posts with comments)

Each comment requires two representations.

**Aggregate file `_data/comments/<slug>.yml`:**
```yaml
- date: YYYY-MM-DD HH:MM:SS +0000
  id: '<integer>'
  message: '<p>Comment text here.</p>'
  name: Commenter Name
  wordpress_url: https://blog.mithis.net/archives/...#comment-<id>
```

**Directory `_data/comments/<slug>/comment-<id>-<YYYYMMDD>-<HHMMSS>.yml`:**
```yaml
date: YYYY-MM-DD HH:MM:SS +0000
id: '<integer>'
message: '<p>Comment text here.</p>'
name: Commenter Name
wordpress_url: https://blog.mithis.net/archives/...#comment-<id>
```

The filename convention is `comment-<id>-<YYYYMMDD>-<HHMMSS>.yml` (zero-padded date/time,
matching the existing 10 individual comment files under `_data/comments/`).

#### A-2.8 Sidebar category counts

The sidebar currently uses **hardcoded static integers** for category post counts (e.g.
`Hardware (3)`). These must be updated manually when posts are assigned to a category.
See §C-1 for the dynamic-count USER-DECISION item; until that is resolved, maintain
the integers manually.

### A-3. Scaffold script: `scripts/new_post.py`

**Location:** `scripts/new_post.py` (Python, matching the project's `uv run` harness;
no Ruby or shell wrapper needed since all other scripts are Python under `scripts/`).

**CLI:**
```
uv run python scripts/new_post.py \
    --title "Post Title Here" \
    --slug my-post-slug \
    [--date YYYY-MM-DD]            # defaults to today (ISO 8601 local)
    [--categories slug1,slug2]     # comma-separated slugs; default: uncategorized
```

All flags:
- `--title TEXT` (required): post title; used verbatim in `title:` front matter.
- `--slug TEXT` (required): the URL slug; used in the filename and `permalink:`.
- `--date YYYY-MM-DD` (optional): defaults to `datetime.date.today().isoformat()`.
- `--categories TEXT` (optional): comma-separated category slugs from the 22+1 list;
  defaults to `uncategorized`.

**Behavior:**
1. Derive the output path: `_posts/<date>-<slug>.md`.
2. If the file already exists, print an error and exit non-zero (refuse to overwrite).
3. Write the file with correct stubbed front matter (new-post format — no `wordpress_*`
   keys):

```python
# Template embedded in the script (not a separate file):
TEMPLATE = """\
---
author: mithro
categories:
{categories_yaml}
date: {date} 12:00:00 +1000
excerpt: 'TODO: Add 1-2 sentence summary here ending with ...'
layout: post
permalink: /archives/{primary_category}/{slug}
title: {title}
---
TODO: Write your post content here.

Use Markdown formatting:
- Blank lines between paragraphs
- ``` fenced code blocks for code (with language tag)
- **bold** and *italic* for emphasis
- [link text](URL) for links
- ![alt text](/assets/images/YYYY/filename.png) for images

No hardcoded HTML block elements (div, ul, ol, li, p, h1-h6, table, pre, etc.)
— the content linter will fail the CI build if found.
"""
```

Where `{categories_yaml}` renders as `- slug1\n- slug2` (YAML list items),
`{primary_category}` is `categories[0]`, and `{title}` is the raw `--title` value.

4. Print the path of the created file.

**Implementation notes:**
- The script must be standalone Python (no third-party deps; only stdlib: `argparse`,
  `datetime`, `pathlib`, `sys`).
- Run via `uv run python scripts/new_post.py ...` (consistent with the harness pattern).
- The script lives at the repo root's `scripts/` level (not under `scripts/fidelity/`)
  since it is a workflow tool, not a fidelity harness component.
- Do NOT add it to `pyproject.toml` as an entry-point; the `uv run python scripts/...`
  invocation pattern is consistent with existing scripts.
- The script must validate that each `--categories` slug is in the known 22+1 list, or
  print a WARNING (not an error) if an unrecognized slug is given (allows future categories
  without breaking the script).

## §B — `lint_content` build-time guard

### B-1. Options evaluated

**Option 1 — Jekyll plugin (`_plugins/lint_content_guard.rb`):**
A Ruby `Jekyll::Generator` or `:pre_render` hook that shells out to
`uv run python -m scripts.fidelity.lint_content _posts --asset-root .` and aborts on
non-zero exit. Triggered by every `jekyll build` and `jekyll serve` locally.

Pros: integrated into local `bundle exec jekyll build`; catches violations before site
generation.
Cons: (a) Ruby↔Python invocation via `system()` or backtick — fragile if `uv` is not on
PATH in the Ruby subprocess; (b) Jekyll plugins are excluded from GitHub Pages' safe mode
(GitHub Pages runs `jekyll build --safe` for user sites — this DOES apply to custom-domain
Pages deploys unless the workflow passes `JEKYLL_ENV=production` and does NOT use the
Actions `actions/configure-pages` with `pages_type: jekyll-github-pages`). Looking at
`.github/workflows/jekyll.yml`, the workflow uses `actions/upload-pages-artifact` + the
full Ruby build path — plugins ARE active; (c) adds a Ruby file that any future developer
must understand alongside the Python harness; (d) the plugin would need to handle `uv`
not being installed (CI image may or may not have it pre-installed unless the Gemfile or
workflow installs it).

**Option 2 — CI workflow step (recommended):**
Add one step to `.github/workflows/jekyll.yml`, before `bundle exec jekyll build`, that
runs:
```yaml
- name: Lint post content
  run: uv run python -m scripts.fidelity.lint_content _posts --asset-root .
```
Non-zero exit fails the job and blocks the build+deploy.

Pros: (a) clean separation — Python linter stays Python, Ruby build stays Ruby; (b) the
CI workflow is the authoritative deploy gate; every push to `main` triggers it; (c) no
Ruby↔Python bridge; (d) `uv` is available in `ubuntu-latest` runners (it is pre-installed
as of 2024); (e) consistent with the existing harness invocation pattern; (f) if `uv` is
not available, the step fails loudly (not silently).
Cons: does not catch violations during local `bundle exec jekyll build` (only at CI time).

**Option 3 — Both:**
Plugin for local + workflow step for CI.
Pros: double coverage.
Cons: the Ruby↔Python bridge fragility still exists for local; adds maintenance surface.

### B-2. Recommendation: Option 2 (CI workflow step)

**Reasoning:** The project's stated primary gate is CI — the repo deploys via GitHub
Actions and the design spec (§11) lists "green Jekyll build with zero warnings" as an
objective gate measured at the workflow level. The Ruby↔Python plugin bridge (Option 1)
adds fragility that the project's harness-first, separation-of-concerns architecture
specifically avoids. Option 2 is minimal, self-contained, and leverages the existing
`uv run python -m scripts.fidelity.lint_content` invocation pattern established by P0.

The local-build gap (Option 2's con) is acceptable: `uv run python -m scripts.fidelity
.lint_content _posts --asset-root .` is a one-liner that any author can run before
committing; the authoring doc (`docs/AUTHORING.md`) should document this as the pre-commit
check. Additionally, the authoring doc points authors to the scaffold script which produces
lint-clean output by construction, so violations would only arise from manual edits.

### B-3. Exact YAML edit to `.github/workflows/jekyll.yml`

**Insert immediately before the `Build with Jekyll` step** (after `Setup Pages`, before
`bundle exec jekyll build`):

```yaml
      - name: Lint post content (no hardcoded structural HTML)
        run: uv run python -m scripts.fidelity.lint_content _posts --asset-root .
```

The full `build` job steps after the edit:
```yaml
    steps:
      - name: Checkout
        uses: actions/checkout@v4
      - name: Setup Ruby
        uses: ruby/setup-ruby@4a9ddd6f338a97768b8006bf671dfbad383215f4
        with:
          bundler-cache: true
          cache-version: 0
      - name: Setup Pages
        id: pages
        uses: actions/configure-pages@v5
      - name: Lint post content (no hardcoded structural HTML)
        run: uv run python -m scripts.fidelity.lint_content _posts --asset-root .
      - name: Build with Jekyll
        run: bundle exec jekyll build

          JEKYLL_ENV: production
      - name: Upload artifact
        uses: actions/upload-pages-artifact@v3
```

**Verification:** after adding the step, push to a feature branch and confirm the workflow
passes (lint step exits 0 on the clean corpus). The step should also fail on a test post
containing `<div>some block HTML</div>` (can be validated locally via the Python module
before wiring the CI step).

### B-4. Sequencing note for the guard

Wire the guard AFTER the housekeeping items (§C) are committed, specifically after:
- EOF normalization (§C-2) — to avoid transient `\n\n` endings triggering any future

- The `lint_content.py` polish items (§C-7) — so the guard is wired against the

The sequencing is a code-quality concern (add the hardened linter before the guard), not
a correctness concern.

## §C — FOLLOWUPS P5 housekeeping rollup

Each item has: (a) exact file(s)/change, (b) gate per item, (c) scope decision.

### C-1. Sidebar dynamic counts (USER-DECISION)

**Item:** Replace the 22+1 hardcoded `(N)` integers in `_includes/sidebar.html`'s
`<select>` options with Liquid expressions that compute each category's actual post count.

**File:** `_includes/sidebar.html`

**Proposed Liquid per option:**
```html
<option value="{{ '/archives/category/hardware/' | relative_url }}">Hardware
  ({{ site.posts | where_exp: "p", "p.categories contains 'hardware'" | size }})</option>
```

This requires 22+1 such expressions. Jekyll evaluates these at build time (not runtime),
so there is no performance concern.

**USER-DECISION required:** The sidebar's current HTML is inside a `<select>` dropdown.
The `(N)` integer is inside the `<option>` text. While the Liquid expression works
syntactically, it makes the file harder to read. More importantly:

- **Hierarchical slug conflict:** `rcs-darcs` and `rcs-tailor` are slugs used in
  `categories:` front matter but they have unusual names. The expression
  `"p.categories contains 'rcs-darcs'"` correctly counts posts with `categories: [rcs-darcs]`.
  This is fine.
- **HDMI2USB double-counting risk:** Posts in `hdmi2usb` also have `timvideos-us` in their
  categories (multi-category). If dynamic counting is enabled, the `timvideos-us` count
  will include HDMI2USB posts (correct per the oracle) and the `hdmi2usb` count will show
  only the HDMI2USB-specific posts (also correct). This is the intended behavior.
- **Sidebar counts vs. live WP oracle:** The PSC phase set sidebar counts to the live WP
  oracle values. If dynamic Liquid counts are used, they will automatically reflect any
  future post additions or re-categorizations — which is the desired long-term behavior.
  However, if there are any future corpus gaps (posts the PSC systemic pass may have
  missed), the dynamic counts will diverge from the WP oracle. The USER must decide:
  (a) switch to dynamic counts now (auto-corrects with corpus), or
  (b) keep static integers (faithful to WP oracle even if corpus is incomplete).

**Recommendation:** Switch to dynamic Liquid counts **after** any pending corpus-
completeness work (the FOLLOWUPS systemic multi-category under-import pass) is done.
If the corpus is oracle-complete, dynamic = static. If not, dynamic would expose the gap.
For P5 now: **DEFER dynamic counts** — keep the PSC-set static integers; add a YAML
comment in `sidebar.html` noting the dynamic-count option with the Liquid form and the
reason it is static. The dynamic conversion is a trivial 1-commit follow-up once corpus
is confirmed complete.

**Gate:** No linter or structure gate change (sidebar changes are not linted). Verify:
`bundle exec jekyll build` clean; sidebar renders with correct counts in `_site/`.

**P5 scope: IN SCOPE for the documentation/comment part; DEFER the Liquid conversion.**

### C-2. EOF `\n\n` → `\n` normalization

**Item:** Normalize all `_posts/*.md` to end with exactly one `\n` (strip trailing blank
lines). This is a cosmetic artifact of the WP→MD export; zero render/fidelity impact;
not a linter finding.

**File(s):** All `_posts/*.md` (76 files). The mixed state: R-A's 6 posts were normalized
as a side effect of `<style>` removal; the remaining ~70 still end with `\n\n`.

**How to implement:**
Write a one-shot normalization script at `tmp/p5/normalize_eof.py`:
```python
from pathlib import Path
for p in Path("_posts").glob("*.md"):
    text = p.read_text(encoding="utf-8")
    if text.endswith("\n\n"):
        p.write_text(text.rstrip("\n") + "\n", encoding="utf-8")
```
Run: `uv run python tmp/p5/normalize_eof.py`

Then verify:
```bash
# No files should end with \n\n:
uv run python -c "
from pathlib import Path
bad = [p for p in Path('_posts').glob('*.md') if p.read_text(encoding='utf-8').endswith('\n\n')]
print(f'{len(bad)} files still end with \\\\n\\\\n:', bad)
"
```

Commit as a single mechanical commit: `Normalize EOF trailing newlines in _posts (cosmetic)`

**Gate per item:** zero files ending with `\n\n` after the script; rendered output
byte-identical to pre-normalization (confirmed by jekyll build + structure 6/6); linter 0.

**P5 scope: IN SCOPE.**

**Linter guard for future posts:** The scaffold script (§A-3) produces output ending with
exactly one `\n` by construction (Python string literals end without trailing blank lines;
the template ends with `...\n`). No additional linter rule needed for this.

### C-4. Comment-form both-forms guardrail

**Item:** Address the `_includes/comments.html` assumption that BOTH comment forms exist.
The current include iterates the directory hash (`site.data.comments[slug]` resolves to
the `<slug>/` directory hash when both the `.yml` aggregate and the `<slug>/` directory

**Two-part action:**

**(a) Document in authoring doc (§A-2.5):** Already covered — the both-forms requirement

**(b) Make `comments.html` list-fallback-robust (OPTIONAL but recommended):**
The current include:
```liquid
{% for _pair in comments %}
  {% assign _comment_objects = _comment_objects | push: _pair[1] %}
{% endfor %}
```
When `comments` is a LIST (from `.yml` only), `_pair[1]` is nil (lists don't have
`[1]`). A robust version:

```liquid
{% if comments.first[0] %}
  {%- comment -%}Hash: site.data.comments[slug] is a dir-hash → [key, value] pairs{%- endcomment -%}
  {% for _pair in comments %}
    {% assign _comment_objects = _comment_objects | push: _pair[1] %}
  {% endfor %}
{% else %}
  {%- comment -%}List: site.data.comments[slug] is a .yml list → use directly{%- endcomment -%}
  {% for item in comments %}
    {% assign _comment_objects = _comment_objects | push: item %}
  {% endfor %}
{% endif %}
```

`comments.first[0]` is non-nil only when `comments` is a hash (where `first` returns
`[key, value]`); it is nil when `comments` is a list (where `first` returns the first
item, which has no `[0]`).

**Recommendation:** Implement the list-fallback. It is a 6-line change in
`_includes/comments.html`, zero risk to existing posts (all 6 comment posts have both
forms), and prevents a silent bug if a future comment post is added with only the `.yml`.
